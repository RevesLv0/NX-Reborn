## Newly narrowed conclusions

1. **The examined writer discards close status through its destructor path.** `DscOsalFile::~DscOsalFile` at `0x5a1e4` calls close PLT `0xe704` at `0x5a214`. Its following instructions never test/store the returned `r0`; `0x5a234–0x5a238` replace it with the saved object pointer. `DscFileHandler::writeChunks` (`0x2d590`, symbol size 16072) sets its successful result in callee-saved `r4` at `0x3140c`, calls that destructor through PLT `0xd780` at `0x31418`, then returns `r4` at `0x31428–0x3142c`. Error exits also converge on this cleanup with `r4=0`, e.g. `0x2f8dc–0x2f8e0`. Therefore this writer's normal return is not a test of fclose success. This is a caller-specific finding, not a claim about every possible external caller.

2. **There is no close virtual slot in the recovered DscOsalFile vtable.** Dynamic symbol `_ZTV11DscOsalFile` at `0xa60a0` has size 16. Relocations: RTTI at `0xa60a4`, D1 destructor at `0xa60a8`, D0 destructor at `0xa60ac`. The separate close GOT relocation is `0xa6830`. This resolves the local vtable question; it does not enumerate all dynamic-linker/interposition or outside-library uses.

3. **The taskMain callback is a completion notification, not a success boolean.** At `0x2cc34–0x2cc70`, `DscFileHandler::taskMain` checks object byte `+0x64`; when clear it calls writeChunks at `0x2cc48` and tests its low-byte result against one. Failure enters logging; success skips it. Both paths converge at `0x2cfac`. Callback presence is checked at `0x2cfb8–0x2cfcc`; `0x2d308–0x2d32c` loads the function pointer from `image->(+0x2c)->(+0x10)` and calls it with `(image, 0, 0)`. Memory release follows at `0x2d334`. The two zero arguments do not carry the observed writeChunks result. The same continuation is reached when the byte at `+0x64` bypasses writing. Meaning/name of that byte remains unresolved.

4. **The writer does check write results, separately from close.** Calls to `DscOsalFile::write` via PLT `0xdd74` occur at `0x2f550`, `0x2fc34`, `0x30018`, `0x30454`, `0x30b90`, each immediately followed by a low-byte boolean check. The write implementation begins at `0x5a858`; `0x5a888` calls its imported write routine and `0x5a894–0x5a8a4` compare the returned count with requested count. Thus ignoring close does not imply ignoring every write failure. A conditional `sync` call appears at `0x303dc`; that call alone proves neither per-file successful close nor durable media completion.

## What the completed libmm-photo export adds

`ImageGenerator::captureSaveDone` starts at `0x924f4`. Its decompilation initializes a local storage state to zero, replaces it with the front of a `std::queue<StorageState>` when nonempty, passes it with the queued filename to an indirect callback, then pops nonempty queues. `ImageGenerator::runFromCapture` is exported at **`0x96684`** and includes a literal zero pushed onto a StorageState queue. These queue observations are decompiler-level; queue identity/producer coverage and the enum meaning of zero were not independently resolved here. Independently checked mm-photo bytes establish the `runFromCapture` dynamic symbol entry as `0x96684` (size 10636), and the Notify registration callsite as `0x9677c`: `BL 0x2bef8`, with notification `r1=2`, route argument `r3=3`, and fifth argument zero on the stack (`0x9675c–0x96778`). The PLT entry at `0x2bef8` resolves through GOT `0xfab64`, whose relocation names `DscImage::Notify`. Thus `0x9677c` is the registration callsite, not the enclosing function entry.

`ImageGenerator::SIFListener` at `0x9f080` switches on its first parameter. Case 3 increments a save-callback counter, conditionally decrements another counter when parameter 2 differs from one, calls `sync` when that counter reaches zero, releases capture resources and schedules an idle callback. Case 4 also calls `sync` and schedules an idle callback. These operations do not themselves inspect a close result. The exact idle targets and all queue producers need relocation/data-flow resolution before claiming an end-to-end storage-success contract.

## Preserve these limitations

- Close itself (`0x5ad4c`) leaves fclose's result in `r0` on its open-stream path: call `0x5ad7c`, pointer clear `0x5ad88`, return `0x5ad98`. Its null-stream path retains the incoming `r0`. The Ghidra pointer return type is not source proof; do not state that the wrapper necessarily destroys its return value.
- The direct-call export contains the close thunk and destructor caller, but direct-call coverage cannot rule out all indirect/external calls. The writer/destructor proof above is narrower and stronger than an absence-of-edges claim.
- `DscImage::JpegDoneEx` (`0x7cef0`) decompiles to a callback at singleton offset `+0x24` using fields from its image argument and a zero third argument; `Notify` (`0x89e00`) case 2 sets offsets `+0x24/+0x28/+0x2c`. This cross-check has not proven that taskMain's image callback pointer is JpegDoneEx on every path.
