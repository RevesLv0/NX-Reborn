원본 ZIP의 새 다운로드·해시 검증은 하지 않았다. 삼성 지원 페이지 재조회는 HTTP 403으로
실패하여 공식 버전 목록 확인은 첫 분석 기록을 유지한다. BIN 일치와 제조사 서명 검증은
별개다. 문자 장치는 호스트에 생성하지 않았다. 삭제·고아 inode나 저널 복구 상태는 위
도달 가능한 경로 조사 범위에 포함되지 않는다. inode dump와 rdump는 동일한 debugfs
구현을 사용하므로 서로 독립적인 ext4 구현으로 교차검증한 것은 아니다.

## 새로 확보한 정적 근거

1. `/etc/fstab`와 명시적 systemd mount 유닛의 `/opt`, `/opt/usr` 파티션 번호가 다르다.
   실제 부팅 파티션 지도로 확정하지 않고 부트로더·generator 우선순위 분석 질문으로 남겼다.
2. `allshare-dms.service`의 스크립트는 vconf `db/allshare/status=0`을 설정한다.
   서비스 이름만으로 DMS 서버가 부팅 시 실행된다고 판단할 수 없다.
3. 카메라 직접 시작 설정과 별도의 starter readiness, 하이버네이션 분기·RAM DB staging을
   확인했다. 실제 부팅 순서와 촬영 중 동작은 아직 관찰하지 않았다.
4. 새 장치 라이브러리에서 SD 경로 선택이 `db/deviced/mount_path_option` 값에 의존하는
   경로를 확인했다. `/mnt/mmc`를 모든 모드의 고정 경로로 가정할 수 없다.
5. smart-wifi의 선택 전송 요청과 DLNA 전송 API의 호출 경로를 확보했다.
   전송 wrapper의 반환값만으로 완료·원본 바이트 일치를 판정하지 않는다.

주소·입력 해시·명령어/설정 근거는
`analysis/architecture/BOOT_SERVICES_20261021.md`,
`analysis/architecture/EXPANDED_GHIDRA_20261021.md` 및 대응 evidence에 있다.
함수 항목 수와 디컴파일 수는 기능 수나 전체 분석 완료율이 아니다.

## 보존한 이상과 미해결 의존성

원본 해시와 일치하는 opt 이미지에 대한 `e2fsck -fn`은 확장 속성 블록 1760의 참조 수가
376이며 기대값은 372라고 보고했다. 읽기 전용 검사에서 저널 복구도 생략했다.
이미지를 수리하지 않았으며 추출된 파일·경로 대조에는 불일치가 없었다. rootfs의 동일
검사는 오류 없이 끝났다. 로그는 전체 재현 receipt와 Drive 인덱스 묶음에 보존한다.

정적 의존성 모델의 미해결 3개는 다음과 같다.

- `libboost_thread.so.1.51.0` → `libboost_chrono.so.1.51.0`
- `libproduction-commands.so` → `libwifi-wolf-partner.so.0`
- `libproduction-commands.so` → `libwifi-wolf-samsung.so.0`

이는 장치에서 실제 로딩이 실패한다는 결론이 아니다. ld.so.cache, 상위 객체의 상속
RPATH, 환경 변수, dlopen과 런타임 mount 변화는 현재 모델에 포함하지 않는다.
