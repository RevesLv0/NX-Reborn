# NX500 offline reverse engineering — RUN004

2026-10-21 KST. This pass follows readiness producers, file-worker callbacks,
transfer callback registration and packaged kernel handlers. All conclusions are
static evidence from the verified NX500 v1.12 corpus. No camera program was run.

## New boundaries

- **Next-shot readiness:** section 5 contains a setter for the same byte consumed
  by Linux `User_Spec_Get_Rtos_Pref_Next_Shot_Ready`: selector `0xff`, preference
  offset `0x1c4d`, base `0x85400000`, final byte store at section offset `0x4e2f70`.
  Bounded callers set and clear it around readiness/raw-buffer paths. This links
  a producer and consumer; it does not establish SD-card durability.
- **Capture completion:** the UI file-end path checks both its capture counter
  and the readiness getter. The file-handler worker can call its buffer callback
  after a write error. A callback alone therefore cannot be classified as proof
  that a file was saved successfully.
- **Transfer:** registration and vtable/GOT evidence bind the worker notification
  through the API callback into a GUI idle-dispatch path. The final numeric state
  consumer remains unresolved; HTTP acknowledgement still does not prove remote
  durable storage or complete camera-resource release.
- **Kernel:** 37,167 absolute ARM kallsyms entries were structurally recovered
  from decoded section 2. All 4,795 exported-name string anchors match the mapping
  `decoded offset = VA - 0xc0008000`. Concrete IPCC and HEVC ioctl handlers now
  connect to the previously inspected userspace requests. Their operation-result
  record fields and the ioctl syscall result have separate meanings. Active boot
  slot selection remains unknown, so these are packaged-section-2 conclusions.
